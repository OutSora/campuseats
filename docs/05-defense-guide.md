# Шпаргалка к защите

## Рассказ на 3 минуты

«CampusEats — система заказа еды в кампусе. Мы разделили предметную область на шесть сервисов, по два на каждого участника. Входящий HTTP-трафик принимает Nginx: он маршрутизирует по URI, балансирует Order Service между двумя экземплярами и ограничивает частоту запросов.

Транзакционные данные находятся в PostgreSQL, потому что нужны ограничения и надежные записи. Каталог кэшируется в Valkey по схеме cache-aside. События и уведомления хранятся в MongoDB: документы имеют разные схемы и подходят для архива.

Order Service после записи заказа публикует OrderCreated в Kafka. Kitchen, Notification и Analytics обрабатывают событие независимо. Kitchen публикует следующее событие. Такая EDA уменьшает связанность и позволяет повторное чтение, но дает eventual consistency и требует идемпотентных consumers. Для маленького MVP RabbitMQ был бы проще; Kafka выбрана ради replay, нескольких consumers и будущей аналитики».

## Что показать преподавателю

1. `docker compose ps` — все компоненты.
2. `http://localhost/api/catalog/items` два раза — заголовки `MISS`, затем `HIT` (в PowerShell: `curl.exe -i URL`).
3. `.\scripts\demo.ps1` — полный сценарий.
4. `http://localhost:8080` — topics, messages, consumer groups.
5. `gateway/nginx.conf` — routing, два upstream, rate limit.
6. `services/common/infra.py` — envelope, at-least-once, commit после handler.
7. `kitchen/main.py` — идемпотентный UPSERT.

## Частые вопросы

**Почему не один монолит?**  
В реальном маленьком MVP монолит был бы дешевле. Микросервисы здесь нужны по заданию и демонстрируют независимое масштабирование, владение данными и асинхронную интеграцию.

**Почему 202, а не 200?**  
Запрос принят, но вся цепочка еще не завершена; кухня и уведомления работают асинхронно.

**Почему Kafka не гарантирует exactly-once всей системе?**  
Kafka может дать транзакционные гарантии внутри своего контура, но запись в PostgreSQL/MongoDB — внешняя операция. Поэтому проект использует at-least-once и идемпотентность.

**Что такое consumer group?**  
Экземпляры одного сервиса имеют одинаковый `group_id`, поэтому partition обрабатывает только один из них. Разные сервисы имеют разные groups и каждый получает событие.

**Почему MongoDB — холодное хранилище?**  
Analytics складывает неизменяемые события для редких исторических запросов. В production старые документы можно выгружать в S3/MinIO и оставлять MongoDB как теплый слой.

**Где балансировщик?**  
В `nginx.conf` upstream `order_cluster` содержит два экземпляра, Nginx выбирает их round-robin.

**Что будет при падении Valkey?**  
Исходный каталог остается в PostgreSQL. Текущая учебная реализация вернет ошибку до восстановления; production-вариант должен ловить ошибку кэша и читать БД напрямую.

**Главный известный недостаток?**  
Между commit заказа и публикацией события возможен сбой. Исправление — transactional outbox: событие записывается в той же транзакции, отдельный publisher отправляет его в Kafka.

## План развития

1. Outbox + retry/DLT.
2. Keycloak/OIDC и роли.
3. OpenTelemetry, Prometheus, Grafana.
4. Schema Registry + Avro.
5. Testcontainers и contract tests.
6. Kubernetes/Helm только после стабильной локальной версии.
